## Session types and item time (vault engine parity)

Branch `feat/session-rules`. The vault engine (`osk-learning-shared/scripts/learning.ts`) already applied these rules; the plugin now matches it.

- Which activity: the active activity whose `session_types` lists the session type's note type name (`SessionType.typeName`: OSK slug, else `noteTypeSlug(name)`, the Starter Kit's own slug rule; standalone `<subject>-practice-sessions`). Listed by two: neither. Activities: OSK activities type (slug `activities`, else tagged `type/activity`) inside its folder; standalone: tagged `type/activity` anywhere. Old fallbacks (latest session's link, "Learn {subject}") only without OSK and with no `session_types` value in any note. Otherwise Log practice asks (existing activity: maps and moves the type; new: created on Log practice with the OSK type, template, affixes, tags and first active status; none: remembered as the first offer until reload). `ActivityService` (new). API: `LogRequest.activity` (name/path or null); unmapped → no activity + warning.
- Session notes get `practiced_minutes` (`"<min> [[<note>]]"`, the even split) when the type defines it (standalone session types do). Session note written before the items. A run again (same type tag, date, minutes, items, start time when given) reuses the note, writes nothing on it, does not count a review recorded that day again; its undo keeps the note (`UndoRecord.reused`).
- Item `time_spent` recomputed from the session notes linking to it (`domain/item-time`), in the item's one write, after waiting for the link index; never added to, never lowered (warning), a non-number left alone (warning).
- Activity time: never lowered on its own (`planActivityTime` → `decision`); a notice with Keep (`Manual adjustment` entry from local midnight of `created`, ISO UTC like the engine) / Drop; the choice merges into the last log's undo record (`mergeChanges`).
- Settings: `fields.practicedMinutes` (`practiced_minutes`), `fields.sessionTypes` (`session_types`).
- Tests: domain specs for each rule (engine edge cases: even share with remainder on the first listed, entries summed, unresolved links skipped, conflicts, archived activities, rerun matching), and a whole-log spec on an in-memory vault (`services/test-vault.ts`).
- Deliberate differences from the engine: an item `time_spent` that isn't a number is left alone (the engine overwrites it); a `created` date without time is read as a local day.

## The progression loop follows a chart's bars (#89, branch plugin-chartbars)

On music-notation 0.12.0 (#75: `chartChords`, bars of silence, `onChord`).

- `chartBacking(text, { noteTime, drawn })` reads each chart with `chartChords`: a chord a bar on lines without bar lines (as before, shown names, unreadable ones left out); on measured lines the chords' `beats` (dots, slashes, shared bars), `%` and empty bars held, a bar of N.C. as `{ chord: null, pitches: [], beats }`. A chart without `{time}` gets the note's time signature before reading, so its beats are counted in the meter the loop plays (the source's `time` stays null, `backingMeter` takes the note's).
- Notes: the plugin draws each chart offscreen (`renderBlock('chords', …)`) and passes its `.mn-chord[data-mn-bar]` voicings; when they line up with `chartChords`' chords (same count), each chord plays them (a `{define}` shape, the sound under `{capo}`, which 0.12.0 of the plugin didn't have: it played the written shape); else names. A `{define}` name that doesn't read as a chord plays only with the drawing.
- `BackingTrack.state.chord` from `onChord`; chips lit by chord, a silent bar's chip "N.C."; the trainer still counts `onBar`. Status: `backingBars` (beats summed, part of a bar a bar) "3 bars of 4/4, as the chart's bar lines say".
- Specs failing first: chartBacking (bar lines/dots/slashes/%; N.C. bar; note time 6/8 → 3 + 3; drawn notes for a `{define}` chart under a capo), `backingBars`, `BackingTrack` onChord.

## 0.15.0: music-notation 0.13.0, reliable reload (#90)

- Dependency `@dsebastien/music-notation` 0.13.0 (exact; lockfile updated in place with Bun 1.3.14, still v1). The library's new blocks need no plugin code: `caption: fingering` on chords, `fingering: auto both` on keyboards, `harmonize:` on progressions. Notation guide: one paragraph each.
- #90, found while checking the library in the vault: Obsidian unloads a plugin whose async `onload` is still waiting (an overlapping reload: Hot Reload plus `plugin:reload`, or a disable/enable during a load). `onload` then went on and registered the protocol handler, events, commands and the code block processors on an unloaded instance: nothing removed them. Every later load failed ("Action music-practice is already registered as a handler"), and the orphaned instance kept drawing the blocks with its old code. Fixed: `onunload` sets `unloaded`, and `onload` stops after `loadSettings` when it is set (spec reproduces the overlap and failed before). The protocol handler goes through `registerProtocolHandler`, which logs a warning instead of failing the load when an earlier instance still holds the action.
- Checked in the vault before the release with the library's test build: captions (row, half step down, left-hand rootless voicing), two harmonized sections, light and dark themes. A window reload cleared the orphaned instance.

## 0.15.1: one live instance per window (#90)

- Checked 0.15.0 in the vault with overlapping reloads (two and three disable/enable cycles a few ms apart): the new instance failed at its first step, "Attempting to register an existing view type music-practice-whats-new", and registered no block language. Cause: Obsidian's plugin manager starts a second instance while the first one still loads, tracks only the second, and never unloads the first. The 0.15.0 guard (stop when unloaded mid-load) can't help: nobody unloads the first one.
- Fix: `src/app/single-instance.ts`. `onload` claims Obsidian's App (a symbol on it) before it registers anything and unloads the instance it replaces (its onunload and register callbacks free the view type, the protocol handler, the processors and the events; its own onload then stops on the `unloaded` guard). `onunload` releases the claim only when it still holds it. Specs for the claim.
- Checked in the vault with the build: two and three overlapping cycles leave one loaded instance with all 10 languages registered and no error (0.15.0: registered 0, a plugin failure).
