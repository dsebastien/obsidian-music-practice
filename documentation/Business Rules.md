# Business Rules

This document defines the core business rules. These rules MUST be respected in all implementations unless explicitly approved otherwise.

---

## Configurable rules

- Every number in these rules (mastery levels, review intervals and multipliers, due-soon window, score weights, plan split, minutes and items per block, warm-up kinds) is a setting (`PracticeRules`, #27). The values written below are the defaults applied on install. Domain code never hardcodes them; it takes the rules as a parameter.
- With the Obsidian Starter Kit, its note types (status values, roles, stamped dates) stay the source of truth for what they define; plugin settings fill the rest (#27, to review).

## Note model source

- With the Obsidian Starter Kit (OSK) available, its note types are the only source: status values and roles, folders, affixes, templates and date stamps come from OSK; plugin settings cover review, score, plan, rubric and property names (#27).
- Without OSK, the standalone model applies (#4): learning types are inferred from notes tagged `type/<domain>/<subject>/<kind>` (only the configured domains, `music` by default) (or `type/<domain>/<kind>`) whose mastery property holds a level; status values are `<level number> - <level name>` from the settings; one session type per subject, with the folder pattern and name suffix from the settings; the plugin stamps the started and mastered dates itself.
- Detection runs on load, on OSK note type changes and before each command; switching between the two never changes notes.

## Learning notes

- Tags are matched without `#` and regardless of case, whether `tags` is a list or text. When several learning types match a note, the most specific one (most tags, then longest type tag) wins.

- A learning note type is a type whose status uses the numbered mastery scale (10 … 60) and that defines the practice field `date_last_practiced`. With the Obsidian Starter Kit (OSK), types are read from OSK (explicit status); without it, from the plugin's own note model settings.
- Its notes carry the type's mandatory tags. The kind (chord, scale, technique, exercise, arrangement…) is the last segment of the type tag `type/<domain>/<subject>/<kind>`.
- Module fields are optional per type and used only when the type defines them: `date_last_practiced`, `bpm_current`, `bpm_target`, `priority`, `prerequisites` (links to learning notes), `theory`, the review fields (`last_reviewed`, `review_interval`, `review_count`, names configurable to match the Kanban Action Planner) and the duration field (`time_spent`).
- Nothing is hardcoded about instruments, types, folders or labels: a new instrument is new note types, never a code change.

## Mastery scale

- Numbers and roles are shared by every domain; each type names its own levels. 10 backlog (Want to learn), 20 active (Learning), 30 active (Can play slowly), 40 active (Can play at tempo), 50 active, on the way back (Rusty), 60 done (Mastered).
- The engine reads only the number in front of a status value, never the label. When it must write a level (a failed review drops 60 to 50), it writes the type's own label for that number.
- Entering 20 and 60 stamps dates (`date_started`, `date_mastered`, `dates_mastered`). **Single writer**: when OSK runs automations, the plugin never stamps these dates.

## Rubric (shown when changing mastery, per kind)

- Chord: 20 shape known; 30 every string rings; 40 switches in time at the target BPM; 60 from memory with any transition.
- Arrangement or piece: 20 sections practiced separately; 30 full run-through slowly; 40 full song at tempo with small mistakes; 60 from memory, at tempo, in context.
- Scale, technique, exercise: 20 pattern known; 30 clean at a slow BPM; 40 clean at the target BPM; 60 from memory in any position.
- Reaching the target BPM offers level 40.

## Spaced review (light SM-2)

- Reaching 30 sets the interval to 3 days when it is empty.
- A review sets the last reviewed date, increments the count and updates the interval: good doubles it (cap 90), shaky keeps it, failed resets it to 3 and drops a mastered item to Rusty.
- Status, for items at 30+ with an interval: days since the last review (or the last practice when never reviewed) ≥ interval is overdue; ≥ interval − min(3, ⌊interval / 3⌋) is due soon; otherwise current. Mastered items stay in review.

## Practice score (higher = practice sooner)

- Priority: 70 − priority number (10 Top → 60 … 60 Very low → 10); 25 when TBD or missing.
- Staleness: with an interval, min(days since practiced / interval, 3) × 10; without, min(days since practiced, 30); 30 when never practiced.
- BPM gap: (100 − min(BPM progress %, 100)) / 5 when both BPMs are set.
- Unlocks: 3 per learning note still at 10 linking to the item (max 5 counted).
- Rusty: +10 at level 50.

## Ready to learn, focus, unlocks

- Ready to learn: level 10 and every prerequisite at 30+; a prerequisite that doesn't resolve to a learning note counts as open.
- Current focus: items at the type's top priority value, not mastered (1–3 at a time).

## Practice plan

- A session for N minutes split warm-up / focus / review / fun (15/50/20/15 by default, configurable). Focus takes the rounding remainder: the blocks always add up to N.
- Warm-up: active techniques and exercises, lowest level first. Focus: active items, current focus first, then by score. Review: due items, most overdue first. Fun: items at 40+, least recently played first.
- Up to three items per block, five minutes each at least. Minutes per item are whole minutes adding up to the block (the first items take the remainder: 20 over 3 → 7, 7, 6); a log splits its minutes between items the same way.
- Review, warm-up and fun pick first; an item is planned once; focus takes the rest. A block shorter than the minimum per item, or with nothing to offer, hands its minutes to focus. Focus always gets an item when there is one, so a very short session still has something to do.

## Sessions and time

- A practice session note belongs to the session type tagged `type/session/<domain>/<subject>` matching the learning note's `type/<domain>/<subject>/<kind>`.
- Naming: `<date> <focus> (<Session suffix>)`, `<date> (<Session suffix>)` without focus, then ` 2`, ` 3` for further sessions that day.
- It records date, minutes, start time, quality, the practiced notes, the minutes per item and the activity link, as far as the session type defines those fields. Minutes per item (`practiced_minutes`, configurable): `"<minutes> [[<note>]]"` per practiced note, the log's even split; skipped when the session type doesn't define the field (standalone session types define it).
- One log is one session of one instrument: items of several instruments are refused. Instrument-less items (`type/music/exercise`) go to the session type the user picks among their domain's.
- A log is checked in full before its first write (request values, items, session type, levels, session name, activity, timer), then stops an adopted Kanban Action Planner timer, writes the session note (linking the chosen activity by name, even one still to create), then the activity the user asked for (created or mapped), the practiced notes (each computed from its own current frontmatter, not from the cache), then the activity's time. One log runs at a time.
- A run again of the same log reuses that session note: a note in the session type's folder (without its date tokens) with the session type's tag, the same date, minutes and items (by name, any order or case), and the same start time when the log gives one (the request's, or an adopted Kanban Action Planner timer's start). Without a given start time (no timer, none typed; the start time the plugin computes and writes on new notes doesn't count), only a note this plugin created less than 15 minutes ago (`RERUN_WINDOW_MS`; an in-memory map of the session paths it created, path → time, lost on reload: file times can't tell, Obsidian Sync and Android reset them), whatever its start time: two real sessions of the same items and minutes that day stay two notes. Reused: no second note, nothing written on it, and no item update: a request whose values (level, BPM, review, a review already recorded that day aside) would change a practiced note is refused before any write, naming the items; else only the items' time and the activity are recomputed. A log returns once Obsidian's cache holds its new session note (5 s at most), so a run again right after finds it. When the reused note links another activity or none, the activity is left alone, with a warning, without waiting. The original log's undo record stays the last log's (the run again's isn't saved; its own record, marked `reused`, undoes nothing and says so).
- Which activity (the vault's rule, `osk-learning-shared` "Which activity a session counts for"): the active activity whose `session_types` (configurable) lists the session type's note type name. Name: the Obsidian Starter Kit's slug for the type, else its name in lower case with spaces as dashes, other characters dropped (`Guitar Practice Sessions` → `guitar-practice-sessions`; standalone: `<subject>-practice-sessions`). One activity per type: listed by two or more, it maps to neither. Activities: with OSK's activities type (slug `activities`, else tagged `type/activity`) and its folder, every note in that folder without its date tokens (as the vault engine reads them, tagged or not); without OSK or without a folder, notes tagged with the type's `type/` tag (`type/activity`) or a child tag. Notes in the type's archive folder (without date tokens) never count, folder or not. Read once per log.
- Fallback, only without OSK and when no note lists anything in `session_types`: the activity the latest session of that type (by its date) linked to; else the note named after the activity setting ("Learn Guitar"); else "Learn Guitar (…)" when that note carries an activity tag.
- No activity lists the type (or several do), any other vault: Log practice asks once, in the dialog, before Log practice is enabled: an existing activity (closest note names first: name holding the subject, then words shared with the proposed name), a new activity (name from the activity setting, editable), or none. Existing: the type is added to its `session_types` and removed from any other activity listing it (the dialog names them). New: created only on Log practice, with the OSK activities type when available (its folder, in a folder of its own name when most activities have one; its affixes; its template rendered without prompts; its tags; its first active status value; `created` = now, local, when OSK automations don't run), else a note tagged `type/activity` in the folder most activities are in (with `created`); `session_types` = the type; refused when that name exists. None: the session has no activity link; the dialog offers None first for that type until the plugin reloads. Nothing is ever created or mapped without the user's choice. Undo never takes that choice back: a created activity and a mapped `session_types` stay (the undo record keeps `activityChoice`, and undo's notice says it stays).
- The API's request takes `activity` (an activity's note name or path; `null` for none); it must be one of the activities above, else the log is refused before any write. Without it, the rules above apply, except the question: an unlisted type logs with no activity and a warning. The service's `mapTo` (the dialog's existing activity) is checked the same way and moves the type from any other activity listing it.
- Item time (the vault's rule, "Session notes and time"): a learning note's duration (`time_spent`, when its type defines it) is recomputed from the session notes that link to it (tag `type/session` or a child): its `practiced_minutes` entry (`"<minutes> [[<note>]]"`, first wikilink resolved, entries for one note add up), else, when only `practiced` lists it, an even whole-minute share of the session's minutes (practiced notes counted once each, the first listed take the remainder); the sum rounded. Never added to. No session counts it, or the same value: no write. Never lowered on its own: a stored value above the computed one stays and the log warns. A value that isn't a number stays and the log warns. Computed once Obsidian's link index sees the session link to the item (10 s at most for all items; else the item's time isn't recomputed and the log warns), in the same write as the item's other fields.
- The session note carries the time: a log writes no time entry on the activity and never adds minutes to it. It recomputes the activity's duration and last-session fields (the vault's "Activity time" rule, the same as the Kanban Action Planner's "Time from linked notes"): duration = its time entries' minutes (`max(1, round)` each, an entry whose description is exactly one wikilink to a counted session skipped) + the minutes of the session notes linked to it (tag `type/session` or a child tag, a wikilink in the activities field that resolves to it, minutes rounded, above 0); last session = the later of the last entry day (local day of its end) and the last linked date. Nothing to count leaves the duration as it is; never lowered on its own: a stored duration above the computed one stays (the last session date is still written) and the log shows a notice, open until answered, with Keep (the difference becomes a time entry described `Manual adjustment`, from local midnight of the activity's `created` day, else of its file's creation day, for the difference in minutes; started earlier when it would end after now (created today, or a `created` ahead), so it never ends in the future; start and end written as local times without offset, as the Kanban Action Planner and the vault engine write them) and Drop (the duration becomes the computed one); the result notice gives the difference as recomputed then; the choice's changes join the last log's undo record when it is still that log (after a run again, the original log's record, when it holds that session note); undoing the log hides an open Keep/Drop notice; a recompute that changes nothing writes nothing; a time entries value that isn't a list leaves the activity alone (`skipped`). It first waits (10 s at most) until Obsidian's link index sees the new session link to the activity; if it doesn't, nothing is written (`not-linked`, the Kanban Action Planner's Recompute tracked time fixes it later). A session type without the activities field can't link, so the activity is left alone. The entries are read again inside `processFrontMatter`.
- Timer guard: when a Kanban Action Planner timer runs on the log's activity, the log must take it over: the timer is stopped, and its own entry (same start within a minute) is removed from the activity, because the session note holds that time; then the activity is recomputed. If that entry doesn't appear within 10 s, the activity is recomputed without removing it (`missing`): a notice says to delete it if it appears. A log that doesn't take it over is refused.
- The practice timer's log uses the timer's start day and time.

## Writing notes

- Frontmatter changes go through `processFrontMatter`, one transaction per note; number-like text (frets `022100`, codes) stays text.
- Never lose information: existing values are only replaced by the fields the action is about. Minutes are never added to anything (they are recomputed); a duration that isn't a number is never overwritten; existing time entries are kept as they are (only an adopted timer's own entry is removed); the last-practiced and last-reviewed dates never move back (an older review leaves the review counters alone).
- Creating a learning note applies its level like a change: the first review interval from "slow" up, and date stamps when the Obsidian Starter Kit doesn't stamp them.

## Notation (v0.2)

- Notation blocks (`chord`, `chords`, `keyboard`, `fretboard`) are drawn by `@dsebastien/music-notation`; the plugin adds no syntax of its own, so a vault renders the same in Obsidian and on Publish (library loader), apart from the layout settings (see Layout).
- One switch per language, on by default. Registered once the layout is ready, so plugins enabled at startup register theirs first. A language another plugin registered first stays theirs: checked in Obsidian's registry before registering (a refused registration leaks a post-processor), and never retried. A language turned off renders as code until the plugin reloads, which frees it.
- A rendering is destroyed with its section (`MarkdownRenderChild`). Mistakes render inline; the note is never changed, except by an action the user selects (Edit as alphaTex on a text tab, #60; Keep this view, #83).
- New chord notes get a `chord block only when Music Practice draws `chord blocks and the block draws without an error.
- A property name added in a newer version that an older data.json already uses for another property gets an `mp_` prefix.
- New guitar chord notes: the chosen voicing goes to the frets and fingers properties (text; dashes when a fret has two digits) and a ``chord block with `symbol`, `frets`, `fingers` (and `position` only when it differs from the computed one). The block fills the template's empty ``chord block when there is one, else goes under the title. Piano chords get `symbol` + `instrument: piano`. "No diagram" adds neither.
- Chord symbols are parsed by the library (one parser for notes and diagrams).

## Layout (v0.3)

- Layout settings (`notationLayout`): left-handed (off), chord diagrams vertical, fretboards and keyboards horizontal. They reach the library as render defaults (`orientation` per language, `hand: left` only when left-handed); a block's own `orientation` / `hand` wins. Piano chords follow the keyboard orientation (the library's rule).
- An orientation in data.json that isn't `vertical` or `horizontal` falls back to the default; the settings dropdowns refuse anything else.
- Changing a layout setting redraws every block on screen in place (each rendered block is tracked while loaded: reading view, live preview, embeds, canvas); it never re-registers processors. The block switches still re-render reading view.
- Note names (`notationLayout.naming`, music-notation #12): `letters` (default), `solfege`, `german`; any other stored value is `letters`. Display only: reaches the library as the `naming` render default only when not letters (letters output unchanged), never re-reads a block (a block's own `naming:` line wins); a change redraws like the other layout settings. The plugin's own drawings with the library's renderers (drills, click input) draw under `withNaming`; the click input's dot labels follow it (3 characters or more squeezed into the dot). Drills show their prompts (find questions built again from their parts, never by `shownText`: it keeps the "A" of "Find A on string 5"), note buttons, chord and scale choices, feedback and heat map cells in it (`domain/note-names.ts`); answers, `drill_setting`, `drill_stats`, drill note titles and the setup form's key range stay letters. Blocks the plugin reads from note text (`chordCharts`, `progressionFences`, and through them `progressionOf`, `chordsOfText`, piece keys, backing loops, drill pools) are read in letters first (`inLetters`: the library's `lettersInBlock`, the block's own naming line taken out; a wrong naming line leaves the block as written). Titles the plugin writes into blocks (Easiest way, Triads) go through `titleShown` (the library never rewrites a `title:` line). Modal hints (Add a learning note, near matches, notices), note titles and properties stay letters.
- Root marks (`notationLayout.rootMark`, music-notation #14): `color` (default), `shape`; any other stored value is `color`. Reaches the library as the `rootMark` render default only when not color (output unchanged), a block's own `root-mark:` line wins; a change redraws like the other layout settings. The drills and the click input draw under `withRootMark` (with `withNaming`). Settings → Notation blocks → Root marks: Color / Color and shape.
- Volume (#95): tab and score blocks get it too (`TabHost.volume`; their bar has no volume since music-notation 0.18, #82). A change of Settings → Playback → Volume is heard at once: the backing loop gets `update({ volume })`, then the library's `volumeChanged()` makes every playing bar read it (also after a change synced from another device). A volume-only change never redraws the blocks (`drawnPlaybackChanged`: a redraw stopped what played); other playback changes do.
- Layout settings apply in Obsidian only; a Publish site gets the same with `window.musicNotationOptions` in its `publish.js` (documented). Blocks that say `orientation:` / `hand:` render the same everywhere.
- Add a learning note, guitar chords: the first 4 voicings are drawn side by side (titled 1 to 4), plus the selected one when it's further down the list (5 columns then); clicking one selects it in place (focus kept) and updates the dropdown; "No diagram" shows no row. Previews use the layout settings. The note still gets one diagram (the selected voicing).

## Chords and scales (v0.4)

- An empty `chord block in a chord note and an empty `fretboard / ```keyboard block in a scale note draw from the note's frontmatter through the library's `blockFromProperties`, with the configured property names and the instrument of the note type (guitar or piano subject; otherwise the library reads the tags). Other notes and blocks with content are unaffected. The note is matched to its learning type the same way as everywhere (`learningTypeOf`).
- Those blocks redraw when the note's metadata changes (`metadataCache` "changed"), only when the properties make a different block; they follow renames (`vault` "rename"); blocks no longer in the page are forgotten; a change of property names redraws them all.
- Add a learning note writes properties only: chord symbol, root, quality, alias, frets and fingers (guitar), pitches (piano chords entered as keys, `C4 E4 G4`, when the type has the property, #76), scale root and type, shape; the note gets an empty block of its language (`ensureBlock`: the template's, else one under the title), only when Music Practice draws that language and, for chords, when the block would draw.
- Chords are typed as a symbol, words, or six guitar frets (recognized; stored compact, without fingers). Frets the library can't name give no note.
- Scales (types that define the scale root and type properties): root and scale/mode from the type's allowed values (else the common roots and scales), shape from the type's shape values; title `<spelled root> <type>[ - <shape>]` (`C# Major` → "C Sharp Major", so sharps survive file names).
- Identify this chord: only on a chord-kind note without a chord symbol whose type defines the chord symbol property; six frets (guitar; numbers padded back to 6 digits) or pitches (piano; lists joined; pitch classes stacked from middle C); one reading applies directly, several open a picker; writes symbol, root, quality (fields the type defines) and adds the alias to the aliases list (a single alias string kept); reports failures. When a guitar or piano chord note has no frets or pitches, or they name no chord, a modal opens on them (#76; other instruments keep the message): clicks change them; readings show as buttons ("Name it X"); near matches show with their missing notes but never name the note. Naming writes, in one `processFrontMatter` and only for properties the type defines (`namedNoteChanges`): symbol, root, quality, alias; when the clicked frets differ, the frets, their fingers (`fingerVoicing`, else none) and the position (`baseFretOf`) when the note has one; when the clicked keys differ, the pitches spelled by their chord (Db F Ab, not C# E# G#), as a list when the note stores a list, and the piano fingering removed. A failure keeps the modal open and says why.
- Click to enter notes (#76): `ClickInput` draws the library's fretboard (frets 0-12, the layout's hand and fretboard orientation) or keyboard (C3-B4, the layout's keyboard orientation) with `pick: true` and `attachPick` (sound from the play options; none when playback is off). A fretboard click sets that string's fret (string 1 the highest), the same place again mutes it; a key click toggles the key. Chosen notes are drawn by the plugin in its own groups after the library's targets (`g.mp-click-dots`, `g.mp-click-near`, `pointer-events: none`, `aria-hidden`), every target has `aria-pressed` (`true` when chosen, else `false`); the drawing is never redrawn. The text field and the drawing stay in sync both ways (`valueOfText`, `textOfValue`: six frets, or keys with octaves; anything else chooses nothing). Keys typed (`typedKeysOf`): one token is a chord first (G7, C7, E9), keys need two tokens or one no chord reads; typed keys keep their spelling, clicked keys are spelled by their chord (`spellKeys`). A click on a chosen note removes it and still sounds it; notes outside the drawing's range stay in the field without a dot; the play options are read when the drawing opens. Near matches (`nearMatches`): only when the notes make no chord the library detects and hold 2 pitch classes or more; the chords of 17 common families on 12 roots that hold every pitch class played and miss at least one note, each set of notes once (the first in this order), fewest missing first, then those rooted on the lowest note, then the family's order; at most 6; missing notes spelled as the chord spells them. Their marks (`nearTargets`): every key of a missing note in the keyboard's range; on a fretboard, the missing notes on muted strings from 2 frets below the lowest fretted note to 2 above the highest (frets 0-4 when none is fretted). Hover or focus marks a near match, a click selects it (it keeps its marks) and, where the form has a chord field, writes its symbol there, clears the clicked notes and moves the focus to the field. Under the drawing: the chord, the near matches, or why neither shows (`clickHint`: fewer than 2 notes, or no common chord holds them). Voicings of a chord: the field follows the clicked frets (their chord, else empty). Add a learning note's piano preview draws the typed keys (`pitches:`). The click drawings are not capped at the preview's 180px height. Used by Add a learning note (guitar and piano chord types), Identify this chord (the modal above) and Voicings of a chord (no chord given, guitar).

## Triads, transitions, tabs and scores (v0.7)

- Triads come from the library (`triadVoicings`, `keyTriads`); a triad note is a chord note of the first guitar chord type (the one the command runs from for "this chord"), titled `<chord name> - <shape> (strings 1-3, root position|1st inversion|2nd inversion)` with the type's value for "Triad" (else "Triad" in the title and no shape); an inversion lists its root-position note (same chord, string set, root position), when it exists, in `prerequisites` as a wikilink. Add a learning note's Triads… puts the triad, its shape and that title in the form, and the note gets the same prerequisite.
- Transitions come from the library (`transition`, `smoothProgression`): from a chord note's frets (else its chord's easiest voicing) to the other note's chord; the next note's own voicing is marked and shown even when it's not among the 4 easiest (when among the 30 considered); Add as note uses the type of the note the chord comes from. Smooth this progression reads ```chords (and ~~~chords) blocks of the note, in order, each chart transposed by its `{transpose}` (spelled for the transposed key, as the chart draws it), consecutive repeats once, at most 16 chords; a step is "in your notes" when a note of the guitar chord type has the same chord symbol and frets.
- Tab and score blocks: alphaTab's UMD script, the Bravura font and the sonivox soundfont are embedded in main.js (virtual modules at build time) and loaded into a window on its first tab block or soundfont play, from a blob URL (workers too); nothing is downloaded. A block draws once it's on the page, with the alphaTab of the window it shows in (popouts), and again when its note moves to another window. While our script loads, an AMD `define` on the page is hidden so alphaTab sets `window.alphaTab`. The plugin's own script needs no check; another plugin's `window.alphaTab` is used only when its `meta.version` is the release the library is made for (`ALPHATAB_VERSION`, equal to the embedded one, checked by a spec); another or no release makes the block say so. A `tab` or `score` block is a plain-text tab when the library's `textTabToAlphaTex` reads it, or it has two staff lines or more (a name or number of up to 8 characters, a bar line, mostly dashes), alphaTex comments left out (`//` only at a line start or after a space: `5//7` is a slide). One the library reads (not a blank stave, which is a template) draws as tablature (#84): its settings lines, then the library's alphaTex of the rest, made in memory at each draw (the note doesn't change); the tab view unless a `staves:` line says otherwise (`defaultStaves: 'tab'`, in score blocks too); the player bar says "Rhythm guessed from the tab" and has **Text** (in the view control, or at the end for drums), which hides the drawing (playback paused) and shows the block's text as code with **Show as tab** and **Edit as alphaTex** under it (the choice survives a redraw in another window); a text tab alphaTab can't draw, or alphaTab not loading, shows that text with **Edit as alphaTex** only. One the library can't read, or a blank stave, shows as code with no button. **Edit as alphaTex** (player bar and text view; in a note only: not on canvas cards, whose text isn't a note), and the command Edit this text tab as alphaTex (`convert-text-tab`, block at the cursor, only when Music Practice draws its language), replace the block's text with its settings lines (`staves:`, `tracks:`, `file:` at the top, kept as they are), the library's alphaTex of the rest, then that text tab in a comment (`/* */`, or `//` lines when the tab holds a block comment), so nothing is lost and the block is no text tab anymore (#60). A block in a list item or callout keeps its place: its lines lose only the opening fence line's own prefix (quote markers, indentation; a `* ` or `- ` in the tab's text stays), and the new lines get that prefix with list markers as spaces of the same width, tabs and `>` kept. The block is the one with the same text in Obsidian's section, else the only one in the note; it's changed through the note's editor in editing view (one transaction, so Ctrl+Z undoes it), else through the file (`vault.process`, lines read with LF or CRLF and written back with the note's own line ending); the notice's Undo puts the text tab back while the converted block is unchanged. View control (#83, from the library's player bar): Tab, Score, Both when a drawn track has tablature; a click redraws in that view without changing the note; **Keep this view** (in a note only) writes `staves: <view>` at the top of the block, replacing a `staves:` line among the settings lines in place, else as a new first line, through the same block lookup and editor transaction (Ctrl+Z) or file as the conversion; a notice when the block can't be found. A tab or score block that fails (an alphaTex mistake, a missing file, alphaTab not loading) shows the message and, folded under it (**Block text**), the block's text with the line the message names marked (#61). Cross-window checks use `instanceOf`, never `instanceof`. Main.js ends with the third-party notices and license texts of what the bundle holds, read from the release build's metafile (#63): every package an input comes from (transitive ones such as tonal included) with its version, license and license file, a library's `THIRD_PARTY_LICENSES.md` after its own license (the music-notation library's names chords-db), and for the virtual alphaTab modules alphaTab (MPL-2.0), Bravura (OFL-1.1) and sonivox (Apache-2.0); packages with the same license text share one entry. ## Plugin lifecycle (v0.15)

- An instance that Obsidian unloads while its `onload` still waits for its settings stops loading: it registers no events, commands, protocol handler or code block processors after the unload, because nothing would remove them (#90).
- The `obsidian://music-practice` handler is registered without failing the load: when an earlier instance still holds it, a warning is logged and the plugin loads the rest.
- One live instance per window: `onload` first claims the window (`claimInstance`, a symbol on Obsidian's App) and unloads an earlier instance that is still live. Obsidian's plugin manager can start a second instance while the first one still loads (two reloads close together) and then tracks only the second: without the claim, the second failed at its first registration ("Attempting to register an existing view type") and drew nothing. `onunload` releases the claim only when it still holds it (v0.15.1).

## Play-along player (v0.17)

- A ` ```playalong ` block (#75) names a recording of the vault: a `file:` line, or a line that is only a link (wikilink, embed, Markdown link) or a path, resolved from the note. Audio mp3 m4a wav flac ogg oga opus 3gp aac; video mp4 webm ogv mov mkv m4v (a video shows its picture). Sections are lines `<time> <name>` (`m:ss`, `mm:ss`, `h:mm:ss`, up to three decimals; the name may be empty), shown in time order. Other lines: a message per line under the player, the rest works. No file, a file not in the vault, or another type: a message and the block text instead of a player. The language has its own toggle (Settings → Play-along, on by default; off shows code) and is left to another plugin that has it; it isn't one of the notation languages.
- Playback: an `<audio>` (hidden) or `<video>` made in the block's document, no native controls, `preservesPitch` on, `playbackRate` = speed (50 % to 125 %, steps of 5 %).
- A-B loop: A and B are set at the playhead; one set past the other swaps them; less than 0.5 s apart is refused; B set with an A turns the loop on; Clear removes both and the loop; Loop needs both. With the loop on, a playhead at or past B (read on each animation frame, and on `timeupdate` and `ended`) starts a new pass at `max(0, A − pre-roll)` (Settings → Play-along → Pre-roll, 0 to 2 s, default 0.2); a seek past B wraps at once. Play with the playhead at or past B starts a pass at A.
- Play starts a pass at A (from the pre-roll) when the loop is on and the playhead is past B or in the pre-roll before A (a section loop set while paused). A pause during a count-in puts the playhead back at the pass's start, so Play again counts in to the same beat. A seek past B during a count-in counts in once, from A. `ended` counts only while playing (not paused, not counting). A rejected `play()` that is stale (an earlier play) or an `AbortError` (interrupted by a pause) is no failure; any other rejection pauses with a notice.
- Count-in (on by default, per player): before Play and before every pass, when a tempo is known: the metronome's count-in bars (at least 1) of beats, beats per bar from the note's time signature as the metronome counts it, else 4, at tempo × speed (20–300), with the metronome's clicks and volume on its audio clock, without starting it; when the lead is longer than the clicks, the clicks start later so the player never starts before now; it ends on the player window's timer; the audio context rests (suspended) 150 ms after the beat it leads to when the metronome isn't running and no other count-in clicks. The recording starts `(start − from) / speed` seconds before the beat after the last click, `from` = `max(0, start − pre-roll)`, so `start` sounds on that beat. Pause cancels it; a seek during it counts in again from there. No tempo: no count-in, and a notice once ("tap the tempo first").
- Tempo (Sébastien, 2026-11-07): the recording's tempo at 100 % is the block's `tempo: <BPM>` line (20–300, `96 BPM` allowed; another value or a second tempo line is named under the player), else a tempo tapped on the player (the metronome's tap rule, divided by the speed), else the note's target BPM (the configured property; a positive number).
